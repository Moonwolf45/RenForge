# RenForge — роадмап архитектуры (универсальность извлечения/доставки)

> Цель: приблизить (не достичь — это невозможно) 100% извлечения и доставки текста.
> План строится вокруг двух идей и набора инвариантов. Статусы отмечаем по ходу.
> Родственные разделы: 02 (экстрактор), 08 (краевые случаи движков), 06 (решения).

## Инварианты (жертвуем — значит это уже ДРУГОЙ продукт)
- Оффлайн, без Ren'Py SDK и без установки Python у пользователя.
- Редактируемый человеческий перевод, распространяемый как мод.
- Crash-safe доставка; язык игры не переключаем (не травим `_preferences.language`).
- Универсальность Ren'Py 6.10 → 8.5. Регресс-дисциплина (bench). 6 локалей синхронно.
- → Живой MT/OCR-оверлей ВНЕ роадмапа (нарушает инварианты; отдельный продукт).

## Принципы
1. **Измеряй, прежде чем строить вслепую.** Сначала делаем покрытие измеримым на конкретной
   игре, потом бьём туда, куда показывают данные.
2. **Аддитивно и обратимо.** Новые каналы — за флагом, с try/except и фоллбэком; работающее не ломаем.

## Ключевой инсайт (почему 100% недостижимо)
Извлечение статично (литералы из AST), доставка — рантайм-матчинг по ТОЧНОМУ тексту.
Мост — исходный текст. Ren'Py-интерполяция `[var]` берётся отлично (say-фильтр видит текст ДО
подстановки → переводим шаблон). Слепая зона — сборка на стороне Python (`+`/`.format()`/`%`):
строка становится целой ДО любого хука. Универсальное «горлышко» есть только на слое рендера
(`Text`-displayable), но там текст уже ФИНАЛЬНЫЙ (значения подставлены) → «увидеть можно всё,
перевести — нет» (ключи неограниченны). Отсюда фазы ниже.

  отчёт в UI (opt-in «диагностическая сборка»). Классификация против БД: «видно в игре, но нет

  **Переоценка (см. «Оценка 0.2/3.1» ниже): без привязки к версии — решение писать/не писать
  принимается ПОСЛЕ данных 0.2, не раньше.**

## Оценка 0.2/3.1 (v1.3.0 → перенос в план 1.4+)

Проведена независимая оценка сложности/рисков перед стартом 0.2 (24.07.2026). Вывод: **обе
фичи откладываются**, но по-разному — 0.2 переносится на 1.4 как самостоятельная задача, 3.1
снимается с привязки к любой конкретной версии.

**0.2 (рендер-хук диагностика) — сложность средняя-высокая, риск средний, инфраструктурный
(не разрушительный).** Все существующие каналы (K1 say/menu, K2 ui, K3 input, K5 uitext, K6
early) патчат ИЗВЕСТНЫЕ Python-функции/атрибуты (`store._`, `renpy.ui.text`, `renpy.input`) —
monkey-patch на уровне API, ~270 строк зашитого кода суммарно. 0.2 требует патч на уровень
рендер-объекта движка (`Text`-displayable) — вызывается на каждый кадр, а не один раз при
построении строки. Риски: (а) hot-path — потенциальный FPS-дроп на насыщенном UI, не только
«шум лога», как сформулировано изначально; (б) внутренняя структура `Text`-displayable менее
стабильна между Ren'Py 6.10→8.5, чем публичный API — более хрупкая точка интеграции для
диапазона версий, который проект обязан поддерживать; (в) объём и разнообразие source'ов текста
на этом слое существенно больше, чем на уровне say-фильтра — фильтрация мусора сложнее, чем
дедуп в 0.1. Смягчающий фактор: фича opt-in и диагностическая, ничего не доставляет — при сбое
не может сломать существующую доставку, только собственный диагностический режим.

**3.1 (pattern/format-aware доставка) — сложность выше заявленной `E:выс`, риск качественно
другого типа.** В коде и журналах — 0 строк заготовок (только зафиксированное в 08 решение
намеренно НЕ извлекать `.format()`/`%`-строки текущими средствами). Требует три независимых
новых подсистемы с нуля:
1. **Извлечение шаблонов** — парсинг `ast.BinOp`(конкатенация)/`.format()`/`%`-форматирования
   с реконструкцией шаблона и позиций подстановки (сегодня экстрактор такие строки осознанно
   отбрасывает, целиком).
2. **Модель данных** — `ExtractedString`/`DbEntry` сегодня плоские `original`/`translation`;
   под шаблон нужна структурированная сущность (префикс/слот/суффикс) + структурированный
   редактор в UI (не в оценке `E` изначального roadmap).
3. **Реверс-матчинг на доставке** — по финальному тексту (данные 0.2) восстановить, какие
   подстроки статичные, какие — переменные. В общем случае некорректно поставленная задача
   (сегментация без разделителей между слотами, значение переменной само содержит статичную
   часть шаблона) → гарантированы edge-case баги качественно ХУЖЕ существующих: не «не
   извлекли/не доставили», а «доставили правдоподобный, но семантически неверный перевод» —
   единственный пункт бэклога с риском тихой порчи результата, а не сбоя. Это сильнее нарушает
   принцип №2 («аддитивно и обратимо, работающее не ломаем»), чем любая другая фича плана.

**Связка (Systems Thinking):** 3.1 формально гейтится данными 0.2 — оценить реальную долю
непокрытого текста класса `.format()`/`%` невозможно, пока 0.2 не отработает на пуле игр. Значит
планировать 3.1 к конкретному релизу сейчас — планирование вслепую, что противоречит принципу №1
(«измеряй, прежде чем строить вслепую»), применённому к самому 3.1.

**Решение:** 0.2 → кандидат на 1.4 (самостоятельная, измеримая задача). 3.1 → без привязки к
версии; гейт явно переформулирован как «решение писать/не писать принимается после анализа
данных 0.2», а не «запланировано после 0.2».

**Следующий кандидат:** 0.2, но перенесён на 1.4 (см. «Оценка 0.2/3.1» выше — сложность/риски
не оправданы для минорника 1.3). Для 1.3 архитектурных пунктов роадмапа больше не запланировано.
1.1 закрыт как покрытый K6.
