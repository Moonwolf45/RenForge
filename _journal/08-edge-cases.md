## Извлечение (п.1 / п.2)

### 🟢 `_()` в аргументах `use screen(...)`
- **Симптом:** не извлекались UI-строки `Preferences`, `Load`, `About`, `Help`,
  `CG mode`, `Erotic mode`, `BGM mode`, `Ending Check`.
- **Корень:** `SLUse.args` — это `ArgumentInfo` с `.source=None`; реальные аргументы
  лежат в `.arguments` как `[(имя, выражение)]`, напр. `[(None, '_("Load")')]`.
  Старый код читал `str()`/`.source` и не видел их; плюс не разворачивал `_()`-обёртку.
- **Фикс:** `unpickler.py`, ветка `SLUse` — читаем `args.arguments`, берём позиционные,
  достаём строки через `extract_python_strings` (+ голые литералы через `extract_implicit_string`).
- **Результат:** +194 строки по играм, 0 регрессий. Найдено в sayaka/bibleblack1/2/discipline.

### 🟢 `show text "..."` — текст в Show-стейтменте
- **Симптом:** пропускались строки вида
  `show text "{size=+10}This story is fictional...{/size}" at truecenter` и
  `show text "You can scroll through long phrases using swipes." with dissolve`.
- **Где:** discipline (`day1.rpy`, `script.rpy`), driven и др.
- **Корень:** `Show`-узлы не обрабатывались. `imspec = (name_tuple, ...)`; для текста
  `name_tuple == ('text', '"...литерал..."')`, для картинок `('cg01','a01')`.
- **Фикс:** `unpickler.py` — ветка `Show/ShowImage/Scene`: если `name_tuple[0]=='text'`,
  достаём строковые аргументы (`_()` через `extract_python_strings`, голые — через `extract_implicit_string`).
- **Результат:** discipline +2, driven +6 и т.д.; дисклеймер и подсказка ушли из MISSED.
- **⚠️ Доставка (инъекция) не проверена:** извлекаем как `ui` (канал `translator.strings`),
  но `show text` — это displayable, и не факт, что движок переводит его через строковый канал.
  Отдельный кейс инъекции, проверить позже.

### 🟢 Экранирование `%` (`\%` vs `%%`) — артефакт сравнения, не баг
- Исходник `.rpy` хранит `\%`, скомпилированная `.rpyc` — `%%` (рантайм-форма). Наш экстрактор
  берёт `%%` из `.rpyc` = совпадает с рантаймом → инъекция матчится. В оракул добавлена
  нормализация `%%`/`\%` → `%`, чтобы убрать ложные пары из MISSED/EXTRA.

### 🟡 Голые строки в Python (`.format()`-UI, tooltips, data-списки) — НЕ тащим (решение)
- **Симптом:** оракул по seeds показал «пропуски»: `text "...{}".format(...)` (screens),
  `self.tooltip = ["..."]` (Python-классы), `'portal': ["Travel to Rosaria..."]` (dict/list данных).
- **Решение: не извлекаем этот класс.** Причины:
  - **Недоставляемость:** `.format()`-строки в рантайме = `"...have 25% modifier"` (число подставлено),
    а текстовый ключ = `"...have {}% modifier"` → при текстовом матчинге НИКОГДА не совпадут.
  - **Риск шума (п.2):** извлечение любых голых литералов из Python захлебнётся в нетранслируемом
    мусоре (ключи, пути, логика). Автор их не пометил `_()` — движок их тоже не переводит.
- **Когда вернуться:** если появится спрос — только узко (напр. `_()`-обёрнутые в Python),
  и с отдельным каналом доставки для шаблонов с `{}` (формат-aware матчинг). Пока вне scope.

### 🟢 `renpy.input("prompt")` — промпт ввода (имя игрока) не извлекался И не доставлялся
- **Симптом:** motherinlust — промпт «What is your name? (Default: {color=...}Honey{/color})»
  оставался английским. Найдено декомпиляцией: `story_intro.rpy:31`
  `$ player_name = renpy.input("What is your name? (Default: ...)", length=20)` — **bare-строка
  без `_()`**. Поэтому её не видел ни наш экстрактор (мы намеренно не тащим голые python-строки),
  ни сам движок (переводит только `_()`-обёрнутое). Повторилось бы на ЛЮБОЙ игре с вводом имени.
- **Фикс извлечения (`unpickler.py`):** `visit_Call` — узкая ветка на `renpy.input(...)`
  (func — Attribute `input`, объект — Name `renpy`): берём первый позиционный строковый литерал.
  Плюс regex-фоллбэк `RENPY_INPUT_REGEX` для Python2/legacy-пути. Извлекается как `type: "python"`.
- **Фикс доставки (`lib.rs` RENFORGE_RUNTIME, «Канал 3»):** движок сырой промпт не переводит,
  поэтому в рантайме оборачиваем `renpy.input` (и `renpy.exports.input`): подменяем промпт по
  словарям (`_renforge_ui_map`, затем `_renforge_say_map`) ДО подстановки `[var]`. Зеркально в `e2e.py`.
- **Проверка (end-to-end через CLI=реальный бэкенд):** новый сайдкар извлёк промпт (total +2),
  set +1, UI +1; в `renforge_translations.rpy` есть и перевод («Как тебя зовут?»), и обёртка
  `renpy.input = _renforge_input`. Тот же код в продуктовом `lib.rs` + сайдкар забандлен
  (`externalBin`) → доходит до юзера в GUI, не только в тесте. Ждёт визуальной проверки запуском.

### ℹ️ Слабость эталон-сканера `qa.py` (не баг продукта)
- Эталонный `.rpy`-сканер недобирает имена персонажей (`Character(_("..."))`),
  звуки/SFX (`{size=+20}SMACK!`) и UI старого формата 6.10 → раздувает список EXTRA.
- На MISSED (главную сторону) не влияет. При желании — улучшить регэкспы сканера.

## Инъекция (п.3 / п.5)

### 🟢 Интерполяция `[var]` — НЕ баг (гипотеза отклонена)
- **Было подозрение:** диалоги driven/seeds в игре оставались английскими → думали, что
  `say_menu_text_filter` получает текст после подстановки `[mc]`.
- **Проверка (renpy/ast.py, Say.execute):** фильтр применяется к `self.what` ДО вызова
  `renpy.exports.say()`, т.е. ДО интерполяции. Фильтр видит сырой текст с `[mc]` нетронутым —
  ровно ту форму, что берёт наш экстрактор (`node.what`). Подстановка идёт позже, по уже
  переведённому тексту (с сохранёнными `[mc]`). Значит матчинг по сырому тексту устойчив к интерполяции.
- **Реальная причина «английских диалогов»:** артефакт ТЕСТА — `e2e.py` переводил только
  первые 300 диалогов; у driven `label start` (`script.rpy`) делает `jump ch1_july_monday`,
  и реальное начало игры (в другом файле) в эти 300 не попадало. У sayaka попало (старт в `script.rpy`).
- **Вывод:** баг инъекции по интерполяции отсутствует. Для осмысленного in-game теста харнессу
  нужно лучше покрывать реальный путь игры (или переводить больше).

### 🟡 Мультиязычные игры: коллизия целевого языка (katawa) — не легаси-баг
- **Симптом:** в katawa (6.10) НИ ОДНА строка не отобразилась.
- **Проверка:** движок 6.10 поддерживает и `python early`, и `say_menu_text_filter`
  (renpy/parser.py, renpy/ast.py) — наш рантайм-файл совместим. Значит дело не в движке.
- **Реальная причина:** katawa — мультиязычная игра (`available_languages` содержит `ru` и др.).
  Мы форсили `change_language("russian")`, игра загрузила СВОЙ `script_ru` → рантайм-текст русский,
  а наш словарь с английскими ключами его не матчит → пусто. (Канал диалогов через `say_menu_text_filter`
  языконезависим, но ключи-английские против русского рантайма не совпадают.)
- **Фикс в харнессе:** `e2e.py` выбирает целевой язык, которого НЕТ в `available_languages`
  игры (для katawa → ukrainian), чтобы рантайм остался на исходном языке и ключи совпали.
- **Реальный edge-case продукта (залогировать):** перевод мультиязычной игры в язык, который у
  неё УЖЕ есть, перекрывается её встроенным переводом. Пользователь обычно переводит в отсутствующий
  язык, так что это редкость, но стоит предупреждать/обрабатывать.

## 📌 ОТЛОЖЕНО (вернёмся): перевод UI на legacy-движках (< ~6.15 / ~2013)

**Статус:** осознанно отложено по решению (не баг, а известное ограничение).

**Суть (два уровня):**
- **Уровень движка (общий):** современный фреймворк переводов (`translator.strings`,
  `translate`-блоки) появился в Ren'Py ~6.15 (2013). На движках старше (6.10–6.14) его НЕТ →
  наш UI-канал `translator.strings[lang]` мёртв на ЛЮБОЙ такой игре, не только на katawa.
- **Уровень игры (специфический):** как именно старая игра переводит UI — bespoke у каждой
  (katawa: `displayDict`/`ui_i18n`). Единого механизма доставки на этих движках нет.

**Почему отложили:**
- Такие игры сегодня редки (фреймворку ~12 лет; в пуле — одна, katawa 2012).
- Диалоги/меню (`say_menu_text_filter`) работают на всём диапазоне 6.10→8.4 — основной видимый
  текст покрыт даже на древних движках.
- Универсального решения для custom-i18n нет; адаптер под одну игру невыгоден.

**План на возврат (если решим массово брать игры < ~2013):**
1. **Общий дешёвый слой:** переопределять `_()`/`__()` в сторе на наш словарь — движок-агностично,
   ловит UI у старых игр, использующих `_()`. (katawa не покрывает — у неё `displayDict`.)
2. **Опциональные адаптеры** под кастомные i18n (напр. рантайм-переопределение
   `displayDict[current_language].<attr>` для katawa-подобных). Точечно, по необходимости.

## Картинки vs текст (сплэши, дисклеймеры)

### 🟢 Сплэш-дисклеймеры — это PNG, не текст (hazelnut, подтверждено декомпиляцией)
- **Симптом:** «DISCLAIMER», «No Generative AI...», «When playing a new build... restart» — английские.
- **Проверка:** декомпиляция `script.rpy` → `image disclaimer = "disclaimer.png"`,
  `image splash2 = "restart.png"`, `image splash3 = "ai.png"`; в `label splashscreen`
  идут как `scene disclaimer` / `scene ai`. Это **изображения**, не текст → извлечению не подлежат.
  Лечится только импортом локализованных картинок (продуктовая фича image-локализации).
- **А вот `centered "Are you eighteen years or older?"` и `centered "This is a build..."`** —
  это ТЕКСТ (dialogue), извлекаются ✓ и доставляемы через say_menu_text_filter.

### 🟢 Процесс: тест должен переводить ВЕСЬ ui-набор, а не только COMMON_RU
- **Проблема:** харнесс переводил лишь опенинг + COMMON_RU, поэтому пользователь постоянно
  находил непереведённые ui-строки (Textbox/Empty/Transparent/Solid, Backer Code, Moan Volume,
  Kinks, Outfits и т.п.). Все они извлекаются как `ui` и доставляемы — это был пробел ТЕСТА, не продукта.
- **Решение (harness):** `dump_ui.py` выгружает все уникальные ui-строки игры (минус COMMON_RU/мусор),
  перевожу их полностью построчно → `dump_ui.py build` мёржит в `<key>.ru.json`. Теперь тест покрывает
  весь интерфейс, и пользователь может подтвердить доставку всего меню. Применено к hazelnut (ui 118→151)
  и motherinlust (ui 79→129). Форматные строки (`{#file_time}%A...`), чистая интерполяция (`[x]%`),
  бренды (Discord) и обрезанные сложные интерполяции — оставляю непереведёнными осознанно.

## Регресс-дисциплина (защита от «Сизифова труда»)

**Правило:** после ЛЮБОГО изменения в `unpickler.py` (или логике извлечения) —
обязательный прогон `python bench.py run` + `python bench.py compare` по всему пулу.
- Дельты должны быть **только неотрицательные**. Любой минус в total/unique = регрессия
  (фикс нового кейса отъел старые строки) → разбирать до снапшота.
- Аддитивные фиксы (новые ветки извлечения) дают `+N` на затронутых играх, `+0` на остальных.
- После подтверждения «только плюсы» — `python bench.py snapshot` фиксирует новый baseline.

**Лог проверок:**
- Фикс `renpy.input` (Канал 3): compare показал hazelnut +1 уник, motherinlust +2 уник,
  остальные +0. Минусов НЕТ → регрессий нет. Baseline переснят. (hazelnut тоже использует
  renpy.input для имени — фикс сработал и там.)

### 🟡 (исходный анализ) Дубль-английский: tl/<english> overlay ломает матч доставки
- **Симптом (тестер):** одна и та же строка (один id `dlc_ExtraScene_3_label_...`) имеет две
  РАЗНЫЕ английские формулировки: в базовом скрипте `original` = "I'm insanely happy to hear
  such a wonderful suggestion!", а в `tl/english` = "I'm so happy to hear such a wonderful
  offer!". Пол-игры на русском, потом резко английский.
- **Корень:** у игры есть overlay-перевод `tl/english/` (переформулированный «полирующий»
  английский) поверх исходного английского в базовом скрипте. В рантайме показывается текст
  из tl/english. RenForge извлёк из source=original → словарь доставки ключается по
  ОРИГИНАЛЬНОМУ тексту. `say_menu_text_filter` в рантайме получает текст tl/english → на
  переформулированных строках ключ не совпадает → строка остаётся английской. Строки,
  совпадающие в original и tl/english, матчатся → русский. Отсюда «половина русская».
  Это семейство «мультиязычной коллизии» (ср. katawa выше), но в ОДНОМ базовом языке.
- **Почему в 1.1 «само работало» (гипотеза):** 1.1, вероятно, форсил язык (change_language),
  и рантайм показывал базовый original → ключи совпадали. В 1.2 язык не трогаем (фикс
  ядовитого _preferences.language) → рантайм на tl/english → мисматч. Трейд-офф того фикса.
- **Немедленный обходной путь для тестера:** переизвлечь с source-language = **english**
  (это tl/english), тогда ключи = тому, что реально показано → русский встанет и на
  переформулированных строках.
- **Запрошенная фича (multi-key delivery):** извлекать ОБА варианта (original + tl/<samelang>),
  группировать по id, дать ОДНО поле перевода на id, а при доставке регистрировать ОБА
  английских текста как ключи → одна русская строка матчится независимо от того, что в
  рантайме. Нужен дизайн (расширение экстрактора: тянуть оба; UI: показать оба english;
  доставка: два ключа на один перевод). НЕ реализовано — обсуждается.
